ISSUE
-----
PCB #1 (debug board): BMI270 accelerometer reads correctly (gravity on
Z ~16500 = 1g at rest, responds to motion, chip ID 0x24, config "loaded
OK"), but the hardware step counter NEVER increments — step output stays
0 even on a real walk. This board "has had trouble before."

PCB #2 (other board): SAME firmware, counts steps perfectly.

=> Same code, one board works and one doesn't => hardware fault on PCB #1.

Step-count output read is CONFIRMED correct in current firmware:
  - read from feature page 0, byte 0 (BMI270_STEP_CNT_OUT_STRT_ADDR=0x00,
    BMI2_PAGE_0), via bmi270_read_feat_page(0, data, 2).
  - A prior regression (commit 3188f8b "BLE connected, no serivces tho")
    had changed this to read register 0x1E — that was wrong for this
    config blob and always returned 0. Now reverted to feature page 0.

Config: ACC_CONF=0x28 (100Hz), PWR_CTRL=0x0E (acc+gyr+temp),
enable = page6/byte3 |= 0x18 (en_detector bit11 + en_counter bit12).
Config blob = standard Bosch bmi270_config_file (8192 bytes,
starts c8 2e 00 2e 80 2e 3d b1).

LEADING HARDWARE SUSPECT
------------------------
The step/feature engine depends on the full 8KB config blob loading
byte-perfect over I2C (256-byte bursts @ 400kHz) AND on clean IMU power.
Basic accel reads do NOT. So a marginal config-blob load (weak/cold I2C
pull-ups, signal integrity, or marginal VDD/VDDIO decoupling on PCB #1)
breaks step counting while leaving accel working. INTERNAL_STATUS=0x01
only confirms the init handshake, not full blob integrity.

NEXT TEST
---------
Flash PCB #2 (working board) with the SAME current firmware, capture its
[DUMP] feature pages, and diff against PCB #1 below.
  - Pages DIFFER  => config blob loads corrupted on PCB #1 => board-level
                     I2C / power signal-integrity issue (reflow BMI270 +
                     decoupling caps + I2C pull-ups; scope SDA/SCL & VDD).
  - Pages IDENTICAL => blob loads fine => suspect the BMI270 die itself.

================================================================
 RESOLVED  (root cause = COLD SOLDER JOINT, not a dead die)
================================================================

The "REPLACE the chip / internal die defect" conclusion above was WRONG
on root cause. Re-placing (reflow/re-seating) the SAME BMI270 on PCB#1
brought the feature engine back to life:
  - pg0 byte4 (step-activity): 0x00 -> 0x03
  - pg0 byte12:                0x00 -> 0x0D
  - live act=:                 frozen 0x00 -> 0x03 (tracks motion)
  - HARDWARE step counter climbed 0 -> 18 on movement (Health "Steps: 18")

So a bad power/ground solder joint was starving the BMI270's digital
feature engine while the more tolerant accel + I2C path still worked
(that's why accel/gyro/config-load all looked fine). The chip itself was
always good. Reflow DID fix it once properly re-seated — the earlier
"reflow won't help" was a reflow that didn't fully remake the joint.

OUTCOME:
  - Both boards now count steps in HARDWARE. Use normal `make program`.
  - SW_STEP_COUNTER software pedometer (sw_step_counter.c) is KEPT as a
    fallback (and may be preferable anyway) but is not required.
  - Lesson: a frozen step-activity output with working accel = suspect
    the IMU's power/ground joints FIRST, reflow thoroughly, before
    condemning the die.
